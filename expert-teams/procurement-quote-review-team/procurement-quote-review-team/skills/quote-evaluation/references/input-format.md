# 本地案例与成员报告格式

所有文件均为 UTF-8。JSON 键、角色 ID、状态值和 CLI 参数保留协议拼写；说明、理由与问题默认使用中文。数字字符串使用十进制文本，例如 `"200.00"`，不使用逗号、货币符号或非有限值。

## 案例 JSON

| 字段 | 含义 |
|---|---|
| `schema_version` | 固定为整数 `1` |
| `title` | 本次比较的名称 |
| `ranking_method` | 必须明确为 `weighted-min-cost-v1`，表示选择下述固定算法；缺失或其他算法会被拒绝 |
| `currency` | 本次比较的明确币种，例如 `CNY`；不能自行补写缺失币种 |
| `horizon_months` | 用户给定的比较月数 |
| `technical_weight`、`cost_weight` | 技术与成本权重的十进制字符串；两者合计为 `100` |
| `criteria` | 最多 10 项要求；每项包含下表字段 |
| `sources` | 原文来源记录：`id` 与相对案例目录的 `path` |
| `offers` | 2–4 份报价；每项包含下表字段 |

要求条目：

| 字段 | 含义 |
|---|---|
| `id` | 唯一且稳定的要求 ID |
| `text` | 用户的原始要求和可执行评价口径 |
| `mandatory` | `true` 为必备条件，不能由低价或其他评分抵消 |
| `weight` | 评分项在技术评分中的权重；必备项使用 `"0"` |
| `max_score` | 评分项的满分；必备项使用 `"1"` |

报价条目：

| 字段 | 含义 |
|---|---|
| `id`、`name` | 唯一报价 ID 与展示名称 |
| `source_ids` | 该报价拥有的原文来源 ID 列表 |
| `currency` | 该报价明确声明的币种 |
| `costs` | 费用条目列表：`id`、`description`、`amount`、`quantity`、`occurrences`、`evidence` |

费用按 `amount × quantity × occurrences` 计算。`amount`、`quantity` 是十进制字符串，`occurrences` 是明确次数；比较期间不会自动转换成收费次数。不能擅自推断月费、年费、含税与否或缺失项目。金额字段与原文不一致时，即使引文存在也必须由成员报告澄清。

本版仅实现以下固定排名法，不能解释为支持任意评分公式。先按下述资格规则排除明确不符合必备要求的报价；全局及未排除报价的比较信息和复核均明确一致后：技术分 = 各评分项的 `score / max_score × weight` 之和（满分 100）；综合分 = `技术分 × technical_weight / 100 + 最低合格总成本 / 本报价总成本 × cost_weight`。综合分从高到低排列，同分并列。所有合格总成本须大于零；零成本不套用此算法。不能拿未合格报价的低价作为归一化基准。用户必须在冻结案例中明确选择 `ranking_method`；若用户要求其他方法，停止并说明本版不支持，不擅自替换。缺失币种、资格未知、全局问题或未排除报价的未知判断和未解决分歧均阻断排名。已排除报价的非必备评价缺口继续展示警告，不改变公式。

技术评分项还应提供可执行量表（什么证据对应什么分数），不能只给“最高 5 分”然后让成员编造映射。

来源 `id` 须以英文字母开头，仅含字母、数字、下划线或连字符，最长 64 字符。来源最多 16 个；比较期间为 1–120 个月。协议字段和数值边界由真实 `inspect` 检查。

每条 `evidence` 是一个原文定位对象：

```json
{"source_id":"a","line":3,"quote":"一次性安装费：1000 CNY，数量 1，收取 1 次。"}
```

`line` 从 1 开始，`quote` 必须逐字位于该行。来源路径是用户明确指定的案例目录内文本，不能用绝对路径、上级跳转、符号链接或远程 URL。每个报价的证据只能引用其 `source_ids` 中的来源。

## 摘要绑定

各成员实际执行 `inspect`，读取真实返回的 `case_sha256`。摘要覆盖本次案例及声明来源；不可手写一个替代摘要。案例、原文或规则变动后，应保存旧报告，重新运行并重新形成记录。

## 技术与独立复核记录

机器可读结构见同目录 [report.schema.json](report.schema.json)。实际脚本还检查角色、完整报价与要求覆盖、数值、输入摘要和原文证据；结构验证成功不能替代这些检查。

本版成员报告使用整数 `schema_version: 2`；案例 JSON 的版本仍为 `1`。技术报告的字段恰为 `schema_version`、`role: "technical"`、`case_sha256`、`assessments`、`notes` 和 `issues`。独立复核报告使用 `role: "verifier"`，并额外包含 `totals`。每份报价和每项要求都要有一条评估记录。未知字段、旧版报告及旧版字符串问题列表均会被拒绝；保留旧稿，依据原文另存本版报告，不能默默改写历史。

| 评估字段 | 含义 |
|---|---|
| `offer_id`、`criterion_id` | 精确对应案例中的报价与要求 ID |
| `status` | 有证据满足用 `pass`，明确不满足用 `fail`，缺失或无法判断用 `unknown` |
| `score` | 评分项使用用户量表内的十进制字符串；无评分或未知时用 `null` |
| `evidence` | 原文定位对象列表，格式同上 |
| `rationale` | 中文判断理由，应解释引文如何支持或不能支持该项要求 |

独立复核员先依据原文保存自己的记录，再读取初评报告；这个规程不构成文件访问隔离。

## 信息说明与未解决问题

所有成员报告都必须有 `notes` 和 `issues`，没有内容使用 `[]`。

- `notes`：中文信息字符串列表，记录正常核验说明、与初稿一致、计算边界或已知失败的解释。它不是待澄清问题清单。
- `issues`：结构化的真实未解决问题列表，字段恰为下表。不得把真实未知、冲突或问题移入 `notes`，也不能通过错分作用范围或类别求得排名。

| 问题字段 | 含义 |
|---|---|
| `scope` | `global` 为适用于全部比较的问题；`offer` 为某一报价的问题 |
| `category` | `eligibility` 为必备条件或准入资格疑问；`evaluation` 为非必备评分、成本或评价口径问题 |
| `message` | 非空中文问题描述，说明缺口及需要澄清的内容 |
| `offer_id` | 仅 `scope: offer` 必须且允许使用，精确对应案例报价；全局问题不可带此字段 |

例如：

```json
{
  "notes": ["已独立复算，A 报价总成本与商务初稿一致。"],
  "issues": [
    {"scope":"offer","offer_id":"B","category":"eligibility","message":"交货承诺未注明工作日还是自然日，无法判定必备期限。"},
    {"scope":"global","category":"evaluation","message":"用户尚未明确评分量表，需确认后再评价。"}
  ]
}
```

已经明确不满足必备条件时，在对应 `assessments` 中写 `fail`、原文证据和理由，可在 `notes` 解释。已知失败与未解决资格问题不同；不要仅为复述失败而创建资格问题。但证据不足、必备条件未知或确有疑问时必须保留，不能把它写成“已确认失败”或信息说明。

## 商务记录

商务报告的字段恰为 `schema_version: 2`、`role: "commercial"`、`case_sha256`、`totals`、`notes` 和 `issues`。独立复核报告中的 `totals` 使用相同结构：每份报价一条，含 `offer_id` 与 `total`。例如 `total: "5800"`；无法确定总额时用 `null`，不能用零表示未知。即使某报价可能被排除，也必须提交完整成本记录和真实问题，不能删去条目或捏造金额。

## 先判断资格，再判断问题是否阻断

所有报告的字段、摘要、来源、完整条目和引文先通过校验，再进行相关性判断。对排除报价也不允许缺行、错引、无效字段或伪造证据。

1. 同一报价在同一必备条件上，技术与复核均为 `fail`，且该报价没有任何必备条件 `unknown`、必备状态冲突或报价级 `eligibility` 问题时，资格可确定为 `excluded`，记录排除要求及原因。
2. 必备条件未知、必备状态冲突或报价级资格问题，使资格成为 `uncertain` 并阻断排名；不能因另一条件已失败而隐藏该不确定性。必备条件一致满足且无资格疑问，才可为 `eligible`。
3. 已确定 `excluded` 报价的非必备评分未知、评分分歧、评价问题或成本缺失保留为非阻断警告。不得为它虚构分数；其他合格报价可在无其余阻断事项时继续比较。
4. 任何全局问题、资格不确定，以及所有未排除报价的问题、未知评分、评分或成本分歧、成本缺失仍阻断排名。分类只控制相关性，不能绕过完整校验或真实问题。

例如 C 的交期为 30 天而必备要求为 14 天，技术与复核均有证据判 `fail`、无其他资格疑问时，C 被排除。C 的非必备培训质量仍未知就保持 `unknown`，显示警告，不猜成满分；A/B 的规则、评分、成本及复核均完整一致时可对 A/B 排名。若 C 的必备交期状态仍有冲突，或任一全局问题未解，则不得排名。

## 结果与真实能力

`deliver` 使用三份报告的真实路径，重新读取并核对案例和原文。最多一次有依据的修正，必须保留原始记录。仍有阻断事项时，解释原因并停止最终排名；非阻断警告不等于已解决，不应被删除。

| 结果字段 | 含义 |
|---|---|
| `eligibility` | 每份报价的 `offer_id`、`status`（`eligible` / `excluded` / `uncertain`）、`reasons` 字符串列表、`exclusion_criteria` 要求 ID 列表 |
| `issues` | 完整规范化问题列表，保留 `origin`、`scope`、`category`、`message`、必要的 `offer_id` / `criterion_id`、`kind`（`issue` / `unknown` / `conflict`）及布尔 `blocking` |
| `warnings` | 非阻断事项的中文字符串列表，包括已排除报价的相关评价缺口或分歧 |
| `notes` | 按报告角色标明来源的信息说明列表 |
| `clarifications`、`conflicts` | 仅保留阻断澄清与阻断冲突；非阻断冲突仍可在 `issues` 与 `warnings` 追溯 |

仅对 `eligible` 报价按既定公式计算。全体报价均排除时无可排名对象，不得宣称已有优胜者；有 `uncertain` 或其他阻断事项时交付待澄清档案。

字段格式、引文存在、摘要一致和算术正确不证明成员身份、独立执行、语义正确、供应商真实性或采购合法。实际协作和最终判断需结合宿主真实任务轨迹与用户核对。
