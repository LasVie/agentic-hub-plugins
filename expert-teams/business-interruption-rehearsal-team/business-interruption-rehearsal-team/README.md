# 业务中断演练与复工核验专家团

**1.0.0**。用两种明确的模拟情景练习共享系统停用、人工登记和恢复后的逐项回填。在普通中断阶段保住工作项，在只读或条件不足时停留在待办状态。由主理人和五名成员分别建立依赖、设计离线作业、规划复工、执行情景与独立复盘。

## 安装和运行

在 WorkSwarm 的 **专家管理 → 我的专家 → 专家团 → 创建 → 上传文件创建** 选择原生测试 ZIP。需要支持原生 AgentGroup 的 WorkSwarm、Python 3.10 或更新版本、现有的任务、文件及命令工具，以及你授权使用的模型。选中专家团点 **使用**。给团长提供用户确认的案例绝对路径和一个已存在的可写工作父目录，所有成员在不同的新子目录保存证据。

> 请使用业务中断演练与复工核验专家团 1.0.0。我确认随包 examples/repair-shop.json 的虚构门店规则作为本次演练约定。工作父目录为我的绝对路径。请使用实际任务分派，依赖、离线作业、复工计划、演练记录及独立复盘都要保留。复盘员请先只用原始案例生成独立基线。交付中文手册、轨迹、审计记录和行动清单，逐项说明两种情景的结论。

## 输入格式

案例使用 UTF-8 JSON，以随包例子为准。两至四个有明确负责人的业务流程，两种情景。人员和流程登记限额都是每次模拟中断期的总件数。工作项按到达分钟、编号排序。登记描述的是保留工作项，处理完成与否不由模拟承诺。流程上线后，同一分钟新到工作项按在线路径接收。准备时长来自用户约定，模型不推断具体资源的并行占用。

- 每种情景从第 0 分钟开始中断，到达、目标和截止时间均用整数分钟。
- `readonly` 只允许依据快照核对；`writable` 才代表模拟可写。还需要 `snapshot_verified` 和 `owner_approved`。事件发生不等于完成复工；每个流程须等待依赖和准备时长。
- 已存在同编号、同版本的工作项只记已存在。版本有冲突时保留，超出登记限额时排队，复工条件未齐时继续待办。
- 缺明确负责人、容量、依赖或时间就先澄清。独立记录冲突时最多修正一轮；证据仍不一致则停止核验交付。

## 输出与边界

- `playbook.md` 中文离线和复工手册，附逐情景、逐项结果。
- `scenario-trace.jsonl` 可复核的有序事件。
- `audit.json` 原始输入与六份上下游证据摘要、独立核验和逐项账目。
- `actions.csv` 未满足的门槛和建议的改进责任人。

模拟结果只覆盖提交的约定。工具不会操作真实系统、迁移数据、发消息、授权复工或替负责人承诺行动项。
