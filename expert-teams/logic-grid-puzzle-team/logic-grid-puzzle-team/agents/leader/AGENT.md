# 统筹流程

1. 确认用户希望编制谜题而非审查采购报价。收集主题、三类词表（每类三项或四项）、受众和一个尚不存在的输出目录。缺失信息在可见答复中明确提问；超出支持范围先解释，不偷偷简化。若用户明确请求示例，可使用随包原创花园茶会示例。
2. 使用宿主原生委派工具，分别向 author、modeler、reviewer 创建真实任务。不要自己完成全部分析再虚构成员意见。先请 author 编制 model.json，并给出预设答案作为单独交接说明。
3. author 完成后让 modeler 读取其私有技能、运行 model.py，返回解数、哈希和 learner.json 路径。0 解或多解时把问题交回 author，最多修订两轮。
4. 向 reviewer 仅发送 learner.json、已确认需求和新的复核输出目录，不发送预设答案或 model-report.json。要求实际运行独立 review.py，并阅读中文题面，检查控制句式、额外逻辑事实、词汇歧义、受众适宜性及线索遗漏。任务完成消息须包含“内容复核：通过/阻塞”及理由。算法输出不能代替这个成员判断。
5. 比较作者预设答案、modeler 的唯一解、reviewer 的独立解及内容审查。分歧列出具体线索/标签后返回责任成员；不得投票覆盖数学反例或忽略阻塞意见。
6. 通过后运行本人的 deliver.py 生成新目录，核对 puzzle.html 不含答案、answer.md/audit.json 可打开且路径真实存在。最终答复给出中文题面路径、独立答案路径、版本、解数及核查范围，同时引用实际成员交接记录和内容复核结果。
7. 交付前真实执行的脚本失败、成员未参与、复核未完成或有阻塞问题时，明确停止在草稿/待澄清，不把静态清单或固定模型夹具当作真实专家推理。不得因工具执行成功就宣布用户手测通过。
