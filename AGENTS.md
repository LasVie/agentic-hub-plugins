# Plugin Maintenance: Review, Build, Submit

This repository stores team-developed and tested Skill / SwarmSkill / Plugin source code and ZIP packages suitable for Agentic Hub submission. The Project Lead is Song Haoran. Read this entire file at the start of every task and choose the workflow that matches the user's current instruction. Do not count candidate research, downloaded research samples, scaffolding, or code-only results as delivered plugins.

| Phase | Trigger and responsible role | Outcome |
| --- | --- | --- |
| 1. Review | Read these rules and collect/reuse the member's explicitly supplied name; then assist candidate screening | Skip claims and proven duplicates, update findings, present options, and wait for the user's selection |
| 2. Build | The named user explicitly selects a plugin and asks to start migration/development | Register the claim/task, review reuse permission, prepare a Chinese test package, and collect user test confirmation plus original test screenshots |
| 3. Submit | Current-package testing is explicitly confirmed, original test screenshots and all delivery materials are collected, and blockers are resolved | Push, open the PR with screenshot evidence, verify links/checks, merge, clean the branch, synchronize development records, and hand off for Project Lead acceptance |

**Phase boundaries.** Read these rules and establish the member's name before plugin work. Review ends at the user's selection; selection starts claim registration and source/license review, not automatic submission. Build remains local until the user explicitly confirms testing of the current Chinese package is complete, known blockers are resolved, and original test screenshots plus all delivery materials are available. Only then may the agent push, open a delivery PR, merge, or publish a Release. Reuse valid confirmation and screenshots instead of asking again. Pure repository maintenance PRs for rules, documentation, tools, or CI are exempt from plugin name/test/screenshot gates and plugin tracker registration.

**Agentic Hub ownership.** Song Haoran personally handles Agentic Hub submission, publication, and the associated Hub evidence. Contributors and their agents deliver the tested, Hub-compatible package through GitHub and do not perform those Hub operations. Hub submission/publication and its screenshot are outside the contributor's delivery and completion gates.

**Tracking scope.** `Development Tasks` and linked `Progress Reports` track only development or modification of specific plugin assets, including new development, porting, feature changes, fixes, and upgrades. Phase 1 maintains review information in `Plugin Candidates` only; it does not create development tasks or fictitious progress reports. Record pure repository maintenance changes, validation, and review in the GitHub PR only. Do not create plugin tasks, reports, pending synchronization records, candidates, or assets for that maintenance. For mixed PRs, track only the actual plugin changes. Additional delivery evidence for an asset stays linked to its original task.

## Phase 1: Review (candidates agent)

### Filter First, Then Compare Functionality

1. First read `Candidate ID`, `Candidate Status`, `Owner`, `Duplicate Check`, `Related Assets and Differences`, `Linked Development Task IDs`, and `Notes` in `Plugin Candidates`. Filter using existing findings and claims before reading asset details or downloading upstream materials.
2. **Skip confirmed duplicates.** If `Duplicate Check = Already Covered`, or the notes contain an explicit conclusion of complete functional coverage, do not review it again, download another sample, or include it in this round's recommendations. Preserve the finding and linked Asset IDs. `Same Name - Review Needed`, `Functional Overlap - Review Needed`, and `Not Checked` are unresolved states, not confirmed duplicates.
3. **Skip selected candidates.** During general screening, skip candidates with an assigned `Owner`, an active unreleased user-selection/claim record, live linked development tasks, or `Candidate Status = Planned / Delivered`. Also skip `Deferred / Excluded`. Explicitly cancelled/released selection history and retired Task IDs in Notes/Progress Reports do not reserve a candidate; use its current owner/status/live task links. When the user explicitly asks to continue their own task, hand off ownership, re-review, or add distinct functionality, handle that specific request using the relevant records. Do not overwrite another person's claim or open duplicate tasks for the same candidate.
4. For remaining candidates, search both historical and new assets in `Asset Ledger`. Compare business capabilities across Skill, SwarmSkill, and Plugin assets in particular; include other asset types when relevant. Compare input objects, key actions, outputs, scope, exclusions, and dependencies. The same name or brand, different authors, different packaging, or different integration methods alone do not establish either duplication or a new capability. Narrow the search with categories/functional tags, then inspect relevant details. Also check relevant active/completed development tasks, candidate claims, and linked merged PRs for capabilities awaiting Hub submission and therefore absent from Asset Ledger. Use these development records for deduplication without prematurely registering a ledger asset. Keep an unresolved finding when the available description is insufficient.
5. **Write duplicate findings back in the same review.** For complete coverage, set `Already Covered`; record existing Asset IDs, versions, and the specific coverage reasoning in `Related Assets and Differences`. Append the actual review date, candidate version/source, and comparison evidence to `Notes`. For a completely duplicated candidate that is still unclaimed and has no linked task, the user's authorization permits setting `Candidate Status` to `Excluded`. Preserve the original research, sources, and history. If the pre-write read shows a new claim or task, skip changes to ownership/status, preserve that person's work, and report the conflict.
6. For partial overlap, use `Partial Overlap - Extend Existing Capability`. Describe the existing entry point to reuse and the actual added scope, and recommend extending the existing asset; do not exclude it as a complete duplicate. Use `Confirmed New Capability` when independent functionality is established. If information is insufficient, use the applicable unresolved option and describe the gap. Failure to find an identical name does not mean deduplication is complete.
7. Verify updates by readback, then summarize candidate IDs under confirmed duplicates skipped, claimed candidates skipped, unresolved items, and available choices. Do not claim candidates, create development tasks, or build packages in this phase. Do not repeat a confirmed-duplicate review without new scope or version evidence; inspect relevant changes only when the user explicitly reopens the item.

Write review records in English, for example: `Reviewed YYYY-MM-DD; candidate <version/ref>; compared <Asset ID>@<version>; outcome <Duplicate Check>; reason <input/action/output/scope comparison>.` Do not invent inspected versions or review dates.

## Cancellation: Delete the Task and Release the Candidate

1. **Apply to every actual cancellation, regardless of reason.** When the user cancels/withdraws a plugin development or modification task, or an existing row is explicitly `Cancelled`, locate it by Task ID and re-read its current candidate, owner, status, linked tasks and cancellation evidence. Delete that task's entire row from Development Tasks. Do not retain, hide, archive within that tab, clear only the status, or leave an empty task record as the cancellation outcome. `Cancelled` is a legacy cleanup trigger, not a persistent task status. A temporary Blocked/Paused state without an actual cancellation is not a deletion trigger.
2. **Record the reason before deleting the row.** Append a dated English cancellation entry to the linked candidate's Notes, containing the former Task ID, previous owner, actual reason/source, classification and resulting status. Keep past Progress Reports and real repository/PR evidence as history; an actual cancellation update may be recorded against the retired Task ID without recreating the task. These historical references are not live assignments. Do not invent a technical/license reason when the user has only said to stop.
3. **Classify intrinsic asset blockers as `Excluded / Unassigned`.** If the cancellation is because the plugin cannot be adapted to WorkSwarm/the required host, or a license/permission problem prevents the intended development/port, set Candidate Status to `Excluded` and Owner to `Unassigned`. Record the concrete scope and evidence in Notes and, for a license issue, use the appropriate live License Review option. Do not label a personal lack of account/access as proof of general incompatibility or prohibited reuse. Source review/native implementation rules still apply while work is active; this classification applies when that issue actually causes cancellation.
4. **Release personal or scheduling cancellations as `To Evaluate / Unassigned`.** No service account, unavailable personal access, lack of time, a wish to develop later, a changed personal priority or selection withdrawal releases the candidate for another member. Set Candidate Status to `To Evaluate` and Owner to `Unassigned`; do not use Deferred merely because this member wants to work on it later. If no specific reason was recorded, note that honestly and release to To Evaluate for renewed assessment; ask for the missing reason when appropriate and reclassify if later evidence establishes an intrinsic blocker.
5. **Remove stale reservation links.** Remove the cancelled Task ID from Linked Development Task IDs and any current claim/reservation, keeping the retired ID and reason in Notes/Progress Reports only. Preserve valid duplicate/license findings, upstream research and evidence. An old selection note or historical cancellation report must not cause screening to skip a now-unassigned To Evaluate candidate. On reselection, recheck current findings and create a new distinct Task ID rather than resurrecting the deleted row.
6. **Preserve unrelated live work and delivered assets.** Always delete the cancelled task row, but remove only its claim if other non-cancelled tasks still actively reserve the same candidate. Preserve those task IDs and confirmed owner(s); do not make another member's active work appear unclaimed. Record/report a conflicting request to exclude the whole candidate. When no other active claim remains, apply the reason-based status/Unassigned pair above. Cancellation does not itself delete prior merged packages, Hub submissions or Asset Ledger records.
7. **Make the linked cleanup concrete and verify it.** Re-read immediately before writing, update the candidate and delete the verified task row in one Sheets batch when possible, and delete multiple rows in descending row order. Never delete from cached row numbers or overwrite a newer concurrent claim. Preserve existing table formats, chips, filters and prepared capacity through row 200; repair the native table/filter/validation ranges after row deletion. Read back absence of the retired Task ID, the candidate state/owner/live links and unaffected tasks. If synchronization is partial, repair and report it; do not claim release succeeded or restore a cancelled row from a stale local snapshot.

### Delete Development Branches After Merge (All PRs)

1. After a plugin-development, modification, or pure repository-maintenance PR merges, immediately clean up its temporary source branch in this repository; do not wait for plugin screenshots, Hub review, or Project Lead acceptance. ## Fixed Package Formats: Skills and Plugins Differ

This repository uses native directories plus deterministic marketplace-wrapper ZIPs. See [Format Research](docs/FORMAT_RESEARCH.md) for references and four actual downloaded sample packages. This is the repository delivery contract; the server accepting some more permissive historical formats does not justify relaxing repository test requirements.

### Skill / SwarmSkill

Source: `skills/<slug>/asset.json`, `provenance.json`, `SOURCE_REVIEW.md`, and `skills/<slug>/<slug>/SKILL.md`. `SKILL.md` uses UTF-8; its YAML frontmatter `name` matches the directory name and `description` is nonempty. Slugs start with a lowercase letter, contain lowercase letters/digits/single hyphens, and are at most 64 characters. Repository versions use `x.y.z`; a frontmatter version, if present, must match asset.json.

```text
<slug>-<version>.zip
└── <slug>/
    ├── plugin.yaml            # runtime.type: skill
    └── <slug>/
        ├── SKILL.md           # native Skill entry; no manifest.json required
        ├── scripts/           # optional
        ├── references/        # optional
        └── assets/            # optional, including required source/license files
```

SwarmSkill also uses `runtime.type: skill`, but frontmatter must include `kind: swarm-skill` and at least two distinct `roles[].id` values, and asset.json must identify the asset as `swarmskill`. Do not infer type from whether the name contains “swarm.”

### Plugin

Source: `plugins/<slug>/asset.json`, `provenance.json`, `SOURCE_REVIEW.md`, and `plugins/<slug>/<slug>/manifest.json`.

```text
<slug>-<version>.zip
└── <slug>/
    ├── plugin.yaml            # runtime.type: agent-plugin
    └── <slug>/
        ├── manifest.json      # native Plugin entry; package_type: plugin
        ├── README.md
        ├── skills/<skill>/SKILL.md
        └── tools/             # optional; rails, mcps, etc. may also be included as needed
```

The manifest `id = asset.json.name = plugin.yaml.name`; all three versions must match, and `package_type = plugin`. The root manifest must not contain `persona`, `agent_card`, `model`, `subagents`, `memories`, or `rubrics`. Do not substitute host Extension or Claude marketplace package formats. Every declared Skill, tool, rail, and MCP file must exist, and paths must stay within the package. Even if Hub's structural validation accepts a declaration with missing files, this repository must verify it and perform functional tests.

### Requirements Shared by Both Formats

- Copy scaffolding from `templates/` into `skills/` or `plugins/`, then provide actual metadata, authorship, sources, and independent design. Templates themselves do not count as assets.
- Run `python tools/asset_release.py check <asset-directory>`, then the asset's own tests. Record the environment, commands, results, failure cases, and dependencies. Repository packaging-tool tests do not replace plugin functional tests.
- Run `python tools/asset_release.py pack <asset-directory>`; write the ZIP and `artifact.json` to `releases/<type>/<slug>/<version>/`. The ZIP contains only the runtime payload and marketplace wrapper, without tests, task tables, or development caches in the wrapper. Put any required bundled source/license files inside the inner payload.
- The marketplace outer directory contains only `plugin.yaml`, optional `icon.png`, and one inner directory with the same name. Do not silently overwrite versions. Local references, SHA-256 hashes, and archive paths must be verifiable. Repository ZIPs are limited to 95 MiB to fit GitHub's single-file constraints; the Project Lead decides how larger assets are delivered.
- `audit-upstream` and local validation do not establish a legal conclusion, successful actual execution, or Hub review approval. The four downloaded sample packages are for static research only; do not run them or submit them as team deliverables.
