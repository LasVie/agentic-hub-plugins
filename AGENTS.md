# Plugin Maintenance: Review, Build, Submit

This repository stores team-developed and tested Skill / SwarmSkill / Plugin source code and ZIP packages suitable for Agentic Hub submission. The Project Lead is Song Haoran. Read this entire file at the start of every task and choose the workflow that matches the user's current instruction. Do not count candidate research, downloaded research samples, scaffolding, or code-only results as delivered plugins.

| Phase | Trigger and responsible role | Outcome |
| --- | --- | --- |
| 1. Review | The user requests candidate screening or review; the candidates agent performs it | Update deduplication findings, present options, and wait for the user's selection |
| 2. Build | The user explicitly selects a plugin and asks to start migration/development | Immediately register the claim and task, prepare a test package, and wait for explicit user confirmation that testing of this version is complete |
| 3. Submit | The user explicitly confirms testing of the current version is complete, and known blocking issues are resolved | Push changes, merge the ZIP through a PR, submit to Hub, and complete evidence and final acceptance |

**Phase boundaries.** A review finding does not automatically start Build. Selecting a plugin does not mean testing is complete, and AI self-tests or passing CI do not establish user test completion. The user's explicit completion confirmation for the current test package is the basis for entering Submit; do not repeatedly request the same confirmation when nothing has changed. Until then, Build stops at a testable local package: do not automatically push, create a delivery PR, merge, publish a Release, or submit to Hub. Pure repository maintenance PRs for rules, documentation, tools, or CI do not require plugin user-test confirmation.

**Tracking scope.** `Development Tasks` and linked `Progress Reports` track only development or modification of specific plugin assets, including new development, porting, feature changes, fixes, and upgrades. Phase 1 maintains review information in `Plugin Candidates` only; it does not create development tasks or fictitious progress reports. Record pure repository maintenance changes, validation, and review in the GitHub PR only. Do not create plugin tasks, reports, pending synchronization records, candidates, or assets for that maintenance. For mixed PRs, track only the actual plugin changes. Additional delivery evidence for an asset stays linked to its original task.

**Language and identity.** The same [shared tracker](https://docs.google.com/spreadsheets/d/12MqKOUOb49c9-i4KF_lii5A2TbmsoeJBF9kCwBIO4eM/edit?usp=sharing) contains `Overview`, `Asset Ledger`, `Plugin Candidates`, `Development Tasks`, `Progress Reports`, and `Members`. Write purposes, scope, tags, notes, task names, progress text, and statuses in English. Preserve stable IDs, actual names, URLs, versions, dates, and original source filenames. Historical display names use official English identifiers; this does not authorize renaming upstream packages. `tracking/tracker.json` provides field and workflow mappings. Still read live headers, dropdown options, and target rows before each update; update by ID, re-read before writing, and verify afterward. Do not overwrite other people's progress with old snapshots. If a connection or access is unavailable, report unsynchronized items. Actual plugin tasks may keep a record in `tracking/pending/`; never claim the cloud sheet was updated when it was not.

## Phase 1: Review (candidates agent)

### Filter First, Then Compare Functionality

1. First read `Candidate ID`, `Candidate Status`, `Owner`, `Duplicate Check`, `Related Assets and Differences`, `Linked Development Task IDs`, and `Notes` in `Plugin Candidates`. Filter using existing findings and claims before reading asset details or downloading upstream materials.
2. **Skip confirmed duplicates.** If `Duplicate Check = Already Covered`, or the notes contain an explicit conclusion of complete functional coverage, do not review it again, download another sample, or include it in this round's recommendations. Preserve the finding and linked Asset IDs. `Same Name - Review Needed`, `Functional Overlap - Review Needed`, and `Not Checked` are unresolved states, not confirmed duplicates.
3. **Skip selected candidates.** During general screening, skip candidates with an assigned `Owner`, an existing user-selection/claim record, linked development tasks, or `Candidate Status = Planned / Delivered`. Also skip `Deferred / Excluded`. When the user explicitly asks to continue their own task, hand off ownership, re-review, or add distinct functionality, handle that specific request using the relevant records. Do not overwrite another person's claim or open duplicate tasks for the same candidate.
4. For remaining candidates, search both historical and new assets in `Asset Ledger`. Compare business capabilities across Skill, SwarmSkill, and Plugin assets in particular; include other asset types when relevant. Compare input objects, key actions, outputs, scope, exclusions, and dependencies. The same name or brand, different authors, different packaging, or different integration methods alone do not establish either duplication or a new capability. Narrow the search with categories/functional tags, then inspect relevant details. Keep an unresolved finding when the available description is insufficient.
5. **Write duplicate findings back in the same review.** For complete coverage, set `Already Covered`; record existing Asset IDs, versions, and the specific coverage reasoning in `Related Assets and Differences`. Append the actual review date, candidate version/source, and comparison evidence to `Notes`. For a completely duplicated candidate that is still unclaimed and has no linked task, the user's authorization permits setting `Candidate Status` to `Excluded`. Preserve the original research, sources, and history. If the pre-write read shows a new claim or task, skip changes to ownership/status, preserve that person's work, and report the conflict.
6. For partial overlap, use `Partial Overlap - Extend Existing Capability`. Describe the existing entry point to reuse and the actual added scope, and recommend extending the existing asset; do not exclude it as a complete duplicate. Use `Confirmed New Capability` when independent functionality is established. If information is insufficient, use the applicable unresolved option and describe the gap. Failure to find an identical name does not mean deduplication is complete.
7. Verify updates by readback, then summarize candidate IDs under confirmed duplicates skipped, claimed candidates skipped, unresolved items, and available choices. Do not claim candidates, create development tasks, or build packages in this phase. Do not repeat a confirmed-duplicate review without new scope or version evidence; inspect relevant changes only when the user explicitly reopens the item.

Write review records in English, for example: `Reviewed YYYY-MM-DD; candidate <version/ref>; compared <Asset ID>@<version>; outcome <Duplicate Check>; reason <input/action/output/scope comparison>.` Do not invent inspected versions or review dates.

## Phase 2: Build (After User Selection)

### Claim and Register Before Implementation

1. When the user says to start migration/development of a candidate, re-read its current findings, owner, claim, and task links by `Candidate ID`. For a confirmed complete duplicate, identify the existing asset and skip it. Skip other people's projects by default; continue only after an explicit handoff/reassignment. If the user requests distinct new functionality, return to Phase 1 to verify that difference. Do not repackage the same functionality as a new implementation.
2. Before coding, update the candidate's `Owner`, `Candidate Status = Planned`, and `Linked Development Task IDs`, and append the selection date, scope, and authority to `Notes`. At the same time, create or reuse the `Development Tasks` entry with its Task ID, `[Candidate ID] <Task Name>`, `Component Type`, `Change Type`, `Owner`, `Status`, and `Dependencies`. Use `AH-YYYYMMDD-<slug>` for new Task IDs and verify uniqueness. If the owner is unknown, retain `Unassigned`; `Planned`, linked Task IDs, and the selection note still show that the candidate is reserved. Never infer ownership from an AI account or PR author.
3. Recheck the claim immediately before writing. Batch candidate/task updates when possible, then read back both IDs, owners, and statuses. If concurrent claims conflict, preserve confirmed assignments, report the conflict, and stop creating a duplicate implementation. If only one side was written successfully, repair and verify the linkage before implementation. Start with `Researching` or `In Development`, then continue updating the same row.
4. Do not restart a full-catalog review for a reviewed candidate. At kickoff, check linked assets and relevant capabilities added or changed since the review so new deliveries are not missed. For an independent development request without a corresponding candidate, state `Not Applicable`; do not invent a candidate row.

### Source Review and Native Implementation

1. Locate the actual upstream URL and pinned commit/version. Check root and subdirectory licenses, file headers, media, and dependencies. Run `python tools/asset_release.py audit-upstream <upstream-directory>` to collect hashes and candidate licenses if useful. The AI must still review license coverage and actual use, recording findings in `SOURCE_REVIEW.md` and `provenance.json`.
2. A public repository, downloadable package, Apache-2.0 website footer, or single license field alone does not establish permission to port the materials used. Keep `permission_status: unknown` when evidence is insufficient, and exclude problematic materials from deliverable source and ZIPs. Fill candidate `License Review` using the live options; append specific findings/evidence to `Notes` and `SOURCE_REVIEW.md`, preserving the original research license snapshot.
3. Use `mode: ported` when reuse is clearly permitted. Record pinned sources, actual copied paths, and bundled license evidence, and follow the Licensing and Distribution Requirements below. The Project Lead separately decides any unified license for repository-owned code.
4. When permission is unclear or porting is prohibited, use `mode: native`: create `NATIVE_DESIGN.md` only from public functional descriptions, user requirements, and authorized inputs/outputs, then independently write code, prompts, documents, icons, and tests. Do not give an AI a non-reusable implementation to translate, rename variables, or rewrite and then claim it is original. Record materials already seen. If the development context contains a non-reusable implementation, hand functional specifications to a developer/new AI context that has not seen it. Do not describe independent implementation as an automatic exemption from patents, trademarks, or service terms; present unresolved questions honestly to the Project Lead.
5. Unclear sources do not prevent independent requirements design or repository-tool maintenance, but problematic materials must not enter delivery. Evidence reused across tasks applies to the pinned source; the actual reuse scope and final ZIP still require review.

### Package in Our Format and Hand Off for User Testing

1. Use the templates and fixed formats below to build a Skill / SwarmSkill / Plugin. Preserve source and actual dependencies, and produce a test package installable and runnable in the target host. Local branches and commits may preserve work; do not push, open a delivery PR, merge, or upload to Hub in this phase.
2. Run format checks, the asset's own functional tests, and packaging. Extract the final test ZIP to verify runtime contents, declared paths, and license files. Give the user an accessible test ZIP/inner Skill directory, version, SHA-256, required environment, installation steps, key operations, expected results, and known issues. Packaging-tool tests do not replace asset functional tests.
3. Set task `Status = Ready for Testing` when the package is ready; use `User Testing` when the user starts testing. Record the test package version/hash, validation results, next steps, and missing evidence in `Progress Reports`; keep the candidate `Planned`. Proactively request missing original test screenshots when the user reports that testing is complete or has passed. Collect them locally during Build; once the delivery PR is allowed and exists, upload them to that PR and record the specific evidence permalink under the Screenshot Evidence policy below. The task's `Test Screenshot` field contains evidence links only. Do not fabricate screenshots or substitute logs.
4. **Explicit user test confirmation is a phase gate.** Set `Ready for Submission` and enter Phase 3 only after the user explicitly confirms that testing of the current task/version is complete or has passed and can be submitted, and known blocking issues are resolved. AI self-tests, CI, downloading a package, starting tests, uploading one screenshot, or vague feedback do not establish completion. If testing is complete but issues remain, return to Build for fixes. Do not repeatedly ask for the same valid confirmation.
5. Append an English confirmation record to the original task's linked `Progress Reports`: `User test confirmation: <faithful English rendering>; confirmed by <actual user>; date/time <time>; Task ID <id>; version <version>; ZIP SHA-256 <hash>; known blocking issues <none/resolved details>; evidence/source <actual conversation reference if available>.` Preserve a verifiable basis in the user's actual message. If no message link exists, identify the current conversation rather than inventing a URL. Store screenshots separately in the evidence column; they do not replace confirmation.
6. Confirmation covers only the version and package hash actually tested by the user. Changes to source payload, packaging, or the final ZIP require returning to Build/testing and obtaining completion confirmation for the new package. Repository-maintenance documentation changes that leave the test package unchanged do not invalidate confirmation. User test confirmation is distinct from final `Project Lead Acceptance = Accepted`.

### Candidate Ownership, Project Initiation, and Handoffs

- Link candidates and tasks by stable IDs and retain all linked Task IDs. In collaborative work, preserve one explicit candidate lead and list other contributors in notes. An owner-only assignment before Build may remain `To Evaluate`, but general screening already skips that claim.
- Follow explicit Project Lead assignments or confirmed task allocation. An assigned candidate owner carries into the corresponding task. If the candidate is unassigned and its task has a confirmed assignment, synchronize that owner back to the candidate. Keep both `Unassigned` when neither is assigned.
- When owners differ, check the latest explicit assignment/handoff. Without evidence, preserve both values and report the conflict rather than overwriting. After explicit reassignment, synchronize both sides and log the old owner, new owner, date, and authority in a report linked to the original task. Splitting subtasks does not automatically change the candidate lead.
- Maintain candidate state separately from task progress. The first delivery remains `Planned` from Build through pending submission acceptance. `Delivered` means all agreed first-delivery conditions are satisfied. Track upgrades in appropriate new or linked tasks while preserving historical delivery markers. `Deferred / Excluded` require an explicit decision; Phase 1's exclusion of unclaimed complete duplicates is an authorized exception. Cancelling one task does not automatically exclude the entire candidate.

## Phase 3: Submit (After Explicit User Test Completion)

### Verify Confirmation Before PR and Hub Submission

1. Re-read the original task and user test confirmation. Check `Task ID`, version, final ZIP SHA-256, unresolved issues, and current owner. Without valid confirmation for the current package, remain in Phase 2; do not infer or fabricate historical confirmation. Preserve historical PR/merge records. Outstanding Hub submissions and later package versions must still satisfy this phase gate; do not resubmit an identical ZIP already merged.
2. Set the task to `Submitting` after valid confirmation. Create or update the source branch from current main, push source, actual functional-test records, source review, ZIP, and artifact.json, then open the delivery PR. Do not push plugins directly to main. Include task/candidate IDs, functional differences, pinned sources/license review, the confirmation's linked Report ID, version, and ZIP hash in the PR. Once the user explicitly confirms testing of this package is complete under this workflow, proceed normally without requesting the same submission permission again.
3. Before merging, verify the final ZIP matches the confirmed package, applicable licenses/notices are complete, asset tests/CI pass, and no unresolved blocking issues remain. Verify the PR's actual `merged` status and merge commit; a successful push, open PR, or passing CI is not a merge. Immediately clean up the corresponding temporary branch under the rules in this section.
4. Check the actual `Test Screenshot` evidence and collect the final `Agentic Hub Submission Screenshot` after the real Hub submission under the Screenshot Evidence policy below. Upload original images to the delivery PR's body or dedicated evidence comments, including comments added after merge. Put only the specific evidence permalinks in the two separate tracker columns. If the user reports testing or Hub submission is finished and the corresponding screenshot is missing or inaccessible, proactively ask the user for that screenshot rather than only recording missing evidence. Reuse valid, accessible evidence already supplied instead of requesting it again.
5. Submit to Hub as agreed: for a Skill, select the extracted inner `<slug>/<slug>/` directory in the web interface and let it package the directory; for a Plugin, upload the merged release ZIP. The official CLI/API available at the time may also be used. If a step requires the user to act in the web interface, provide clear instructions and wait for actual results; do not claim submission occurred. When the Skill web interface repackages content, compare payload file inventories/hashes and version rather than assuming the outer ZIP hash is identical. Submitted contents must match the confirmed and merged payload.

### Screenshot Evidence: GitHub PR Originals and Link-Only Tracker Fields

1. **Request evidence at the relevant completion event.** When the user says testing is complete or has passed, check for actual test screenshots of the current version and key operations/results. When the user says Hub submission is complete, check for a screenshot showing the asset name/version and actual submission result or review status. If the corresponding evidence is absent, unreadable, inaccessible, or for another version, proactively ask the user to provide the missing original screenshot in the current conversation or upload it to the delivery PR. If both are missing, ask for both together. Check existing evidence first and do not repeatedly request valid screenshots already supplied.
2. **Upload original images to the delivery PR.** Attach the user's original full-resolution PNG/JPEG screenshots to the PR body or dedicated evidence comments; do not use a screenshot of a spreadsheet thumbnail or an unnecessarily recompressed copy. Label test and Hub-submission evidence separately with the Task ID, Candidate ID when applicable, asset name, version, and tested ZIP SHA-256 where relevant. A comment on the same merged PR may add Hub evidence later; do not open another plugin-delivery PR merely to add screenshots. During Build, collect screenshots locally without pushing or opening a delivery PR before the explicit test-completion gate. Respect the repository's current visibility and check/redact keys, credentials and private information before upload; ask the user for a safe replacement if the image cannot be shared appropriately.
3. **Both tracker screenshot columns contain links only.** In `Development Tasks`, `Test Screenshot` links to the PR body section or comment containing the real test images; `Agentic Hub Submission Screenshot` links to the body section or comment containing the real Hub-submission images. Prefer dedicated comment permalinks, or a verified body-section anchor, so reviewers can find and open the original images. Multiple relevant evidence permalinks may occupy the appropriate cell. Do not embed images, thumbnails, `IMAGE()` formulas, local paths, base64 data, temporary signed image URLs, or Drive links in these two columns.
4. **Verify the actual linked evidence.** Open each permalink and verify its attached images, task/version association and readability before writing it; then re-read the tracker cells. A bare PR URL, an empty/planned comment, logs, sample images or a fabricated link do not satisfy either screenshot field. Use links to the PR discussion, which remain usable after its temporary branch is deleted, rather than links tied to that branch. Report missing repository/connector access honestly; do not make private evidence public merely to make a link work.
5. **Keep screenshot evidence separate from confirmation and acceptance.** Screenshots do not establish explicit user test completion, actual Hub approval/publication, or final Project Lead acceptance. Missing screenshots do not erase an otherwise valid test-completion confirmation, but the original task must retain its missing-evidence record and cannot become `Completed`/`Delivered` until both actual evidence links are accessible and all other delivery gates pass. Continue authorized steps that do not depend on the missing screenshots and use `Awaiting Acceptance` when the existing completion rules require it.
6. **Migrate old evidence without losing it.** When updating an existing task that has an embedded screenshot or another evidence location, first preserve the original, attach it to the task's delivery PR and verify the resulting evidence permalink; only then replace that screenshot cell with the permalink. If no delivery PR is allowed yet or the original/access is unavailable, request the missing input and preserve the existing evidence until migration can be completed. Do not invent a PR or discard the only available screenshot.

### Synchronize the Ledger and Complete Final Acceptance

1. **Synchronize Asset Ledger after merge.** Register a new asset only after the PR actually merged and functional tests passed. Update an existing record by linked ID or append a `New Asset` row with name, type, category, purpose, tags, scope, publisher, version, source, and date. Keep `Historical Asset` for historical-asset upgrades. Before Hub publication, use the actual merged PR/delivery path as the source; do not invent Hub URLs or publication status.
2. Without a Hub ID, use the stable internal ID `repo:<type>:<slug>` and identify it as internal. Record the actual Hub ID separately in delivery.json and update the source to the actual detail page once obtained. Keep internal IDs stable and retain existing historical Hub IDs. Match linked IDs/source URLs first, then names/functionality, to avoid duplicate registration.
3. **Synchronize tasks, candidates, and reports.** Update the original task with its actual merged PR, both screenshot links, and current status. Update the candidate's owner, linked Task IDs, actual duplication/license conclusions, and notes containing the merged version, Asset ID, and Hub status. While evidence, the agreed Hub target, or Project Lead acceptance is outstanding, use `Awaiting Acceptance`; keep a first-delivery candidate `Planned` and leave the completion date blank. A Hub review in progress is `Submitted - Pending Review`, not publication. Preserve dates, task/candidate IDs, completed work, next steps, blockers, and decisions needed from the Project Lead in new reports; do not overwrite history.
4. **Record final Project Lead acceptance separately.** Set `Project Lead Acceptance = Accepted` only after explicit acceptance by Song Haoran. Set the task to `Completed`, enter its actual completion date, and set the corresponding first-delivery candidate to `Delivered` only when functional tests and current user test-completion confirmation are valid, the PR is merged, both actual evidence links are accessible, the agreed Hub submission/publication target is met, the Project Lead explicitly accepts, and the ledger/linked records have been synchronized and verified by readback. Evaluate submission-only and publication-required targets according to the agreement. Test completion does not replace final delivery acceptance.
5. Preserve historical deliveries and claims for upgrades and split tasks. Assess delivery of a multi-task candidate against the entire agreed scope. Verify candidate, task, and Asset IDs, owners, links, and all sheet states after writing. Pure repository maintenance uses a maintenance PR, does not require plugin ZIPs, the two screenshots, or plugin acceptance, and is not registered in tasks/reports.

### Delete Development Branches After Merge (All PRs)

1. After a plugin-development, modification, or pure repository-maintenance PR merges, immediately clean up its temporary source branch in this repository; do not wait for plugin screenshots, Hub review, or Project Lead acceptance. First verify actual PR `merged` status and the merge commit, then check the source repository, branch name, and latest head SHA. Delete only if the branch still points to the merged PR head and no other unmerged PR uses it as a source or target branch.
2. Even when GitHub's “Automatically delete head branches” setting is enabled, verify that this PR's source branch was deleted. If it was not, a maintainer with permission must delete and verify it manually. If permissions or branch protection prevent cleanup, record the branch and reason in the PR; do not claim deletion succeeded.
3. Preserve `main`, the repository default branch, and explicitly retained long-lived or protected branches. If new commits appear after merge, or another unmerged PR depends on the source branch, keep it and explain the remaining work in the PR. Do not delete branches in other contributors' forks or force-delete unmerged local work.
4. Start subsequent changes on a new development branch from current main instead of reusing a merged branch. Delivery/tracking links must use the actual PR, merge commit, or main-branch release path rather than a soon-to-be-deleted branch URL. This cleanup rule also applies to maintenance PRs without creating plugin-tracker entries for them.

## Licensing and Distribution Requirements

The Project Lead approved the following requirements, reviewed on 2026-10-22. They apply to Skills, SwarmSkills, and Plugins. Assess the actual license text, covered materials, and intended use; do not automatically approve reuse based only on a repository name or SPDX label.

1. **Check coverage item by item.** In `SOURCE_REVIEW.md`, record upstream URLs, pinned commits/versions, existing rightsholder statements, reused/modified paths, applicable licenses, and distribution conditions. Check code, prompts, documents, icons, fonts, data, and dependencies separately. Open-source code does not automatically authorize brand assets, third-party data, or API services. Satisfy every applicable license in a mixed-license package. For dual licensing, record the actual choice; do not arbitrarily remove obligations joined by `AND` or invent an `OR` option.
2. **MIT.** When reusing or distributing copies or substantial portions of the software, retain the original copyright and permission notices. This repository requires bundling the complete upstream MIT text, including its disclaimer, and preserving original file headers. Links, SPDX fields, and new copyright notices do not replace original notices. Recording modifications is a repository tracking convention, not a separate MIT requirement. Reference: [MIT license text](https://opensource.org/license/mit).
3. **Apache-2.0.** Under Section 4, provide recipients a copy of the license, place prominent change notices in modified files, and retain applicable copyright, patent, trademark, and attribution notices when distributing derivative source. If the upstream distribution includes NOTICE, retain its applicable attribution content in the package; if none exists, record that fact instead of fabricating one. New team attribution cannot replace upstream notices, and NOTICE must not be used to change license terms. Section 6 does not grant general trademark rights; do not imply official endorsement. Reference: [Apache-2.0 Sections 4 and 6](https://www.apache.org/licenses/LICENSE-2.0.txt).
4. **Other or unclear permissions.** Review other licenses, separate grants, additional restrictions, and compatibility questions against their actual text; do not apply the MIT/Apache conclusions automatically. If a public source has no license or its license does not cover the materials actually reused, keep `permission_status: unknown` and prevent those materials from entering deliverable source and ZIPs. Obtain explicit permission or follow the native-implementation requirements in Phase 2. Not finding a license does not prove the source is closed, and does not permit copying. Reference: [GitHub guidance on unlicensed repositories](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository).
5. **Bundled materials.** For `ported` assets, this repository requires `THIRD_PARTY_NOTICES.md` inside the inner payload, listing upstream sources, pinned versions, original author/rightsholder statements, covered files, licenses, and a modification summary. Store full license texts in `licenses/<upstream>/LICENSE` and applicable upstream NOTICE in the same directory. Keep separate evidence for multiple upstreams and preserve original file headers and other applicable notices. Repository-page or PR links alone are insufficient. Apache change notices must still appear in the modified files; a central modification summary does not replace them. These paths and filenames are repository conventions, not universal license requirements.
6. **Review before release.** Extract the final ZIP and check that every reused path has matching license/notice coverage, change notices are complete, and `license_evidence` paths and hashes match the actual bundled files. Record results and ZIP paths in `SOURCE_REVIEW.md`. The PR must list fulfilled and unresolved conditions; do not merge the asset while any required condition remains unmet. `audit-upstream`, `check`, CI, and Hub accepting an upload do not replace this content review.

This policy does not relicense the entire repository, team-owned work, or upstream materials under one license. AI must not guess copyright ownership, remove upstream authors, or make new relicensing decisions for the Project Lead. Independent implementation must not be described as an automatic exemption from other rights such as patents, trademarks, or service terms.

## Fixed Package Formats: Skills and Plugins Differ

This repository uses native directories plus deterministic marketplace-wrapper ZIPs. See [Format Research](docs/FORMAT_RESEARCH.md) for references and four actual downloaded sample packages. This is the repository delivery contract; the server accepting some more permissive historical formats does not justify relaxing repository test requirements.

### Skill / SwarmSkill

Source: `skills/<slug>/asset.json`, `provenance.json`, `SOURCE_REVIEW.md`, and `skills/<slug>/<slug>/SKILL.md`. `SKILL.md` uses UTF-8; its YAML frontmatter `name` matches the directory name and `description` is nonempty. Slugs start with a lowercase letter, contain lowercase letters/digits/single hyphens, and are at most 64 characters. Repository versions use `x.y.z`; a frontmatter version, if present, must match asset.json.

```text
<slug>-<version>.zip
└── <slug>/
    ├── plugin.yaml            # runtime.type: skill
    └── <slug>/
        ├── SKILL.md           # native Skill entry; no manifest.json required
        ├── scripts/           # optional
        ├── references/        # optional
        └── assets/            # optional, including required source/license files
```

SwarmSkill also uses `runtime.type: skill`, but frontmatter must include `kind: swarm-skill` and at least two distinct `roles[].id` values, and asset.json must identify the asset as `swarmskill`. Do not infer type from whether the name contains “swarm.”

### Plugin

Source: `plugins/<slug>/asset.json`, `provenance.json`, `SOURCE_REVIEW.md`, and `plugins/<slug>/<slug>/manifest.json`.

```text
<slug>-<version>.zip
└── <slug>/
    ├── plugin.yaml            # runtime.type: agent-plugin
    └── <slug>/
        ├── manifest.json      # native Plugin entry; package_type: plugin
        ├── README.md
        ├── skills/<skill>/SKILL.md
        └── tools/             # optional; rails, mcps, etc. may also be included as needed
```

The manifest `id = asset.json.name = plugin.yaml.name`; all three versions must match, and `package_type = plugin`. The root manifest must not contain `persona`, `agent_card`, `model`, `subagents`, `memories`, or `rubrics`. Do not substitute host Extension or Claude marketplace package formats. Every declared Skill, tool, rail, and MCP file must exist, and paths must stay within the package. Even if Hub's structural validation accepts a declaration with missing files, this repository must verify it and perform functional tests.

### Requirements Shared by Both Formats

- Copy scaffolding from `templates/` into `skills/` or `plugins/`, then provide actual metadata, authorship, sources, and independent design. Templates themselves do not count as assets.
- Run `python tools/asset_release.py check <asset-directory>`, then the asset's own tests. Record the environment, commands, results, failure cases, and dependencies. Repository packaging-tool tests do not replace plugin functional tests.
- Run `python tools/asset_release.py pack <asset-directory>`; write the ZIP and `artifact.json` to `releases/<type>/<slug>/<version>/`. The ZIP contains only the runtime payload and marketplace wrapper, without tests, task tables, or development caches in the wrapper. Put any required bundled source/license files inside the inner payload.
- The marketplace outer directory contains only `plugin.yaml`, optional `icon.png`, and one inner directory with the same name. Do not silently overwrite versions.
